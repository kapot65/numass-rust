# 2. Отдельные стадии обработки

- Статус: принято
- Дата: 2026-10-08

## Тип исходных данных

Исходные данные — **синхронизированные осциллограммы**: при аппаратном триггере
с платы приходят вейвформы со **всех включённых каналов**, независимо от наличия
событий. На уровне protobuf точка (`rsb_event::Point`) имеет иерархию
`канал → блок → фрейм`, где фрейм несёт время триггера и сырые отсчёты. Это legacy формат. Внутри обработки мы преобразуем его в иерархию по времени триггера.

Для экономии памяти применяется **программный zero-suppression**, который должен соответствовать аппаратному 1 к 1, но на
практике может «разъехаться». Реализован на стороне сбора в
`tqdc-controller-rust`.

## Обработка данных
Пайплайн обработки [numass-processing](../numass-processing) разбит на три независимые стадии:
- [preprocess](../numass-processing/src/preprocess.rs) - (оцпиональное) преобразование типа waveform -> waveform, с сохранением иерархии (после преобразования из legacy формата). Этап предназначен перевести сырые кадры в **стандартизированный вид**: **осцилограмма с плоской нулевой базовой линией**. Также на этом этапе извлекуются/вычисляются параметры, общие для всей точки. Эти параметры будут проброшены в дальнейшие стадии обработки.
- [process](../numass-processing/src/process.rs) - преобразование типа waveform -> events. На этом этапе **стандартизированные осцилограммы** преобразуются в события. Одна осцилограмма может перейти в 0, 1 или более событий. Пропадает привязка к аппаратному триггеру. Данные переходят в упорядоченную карту (время прихода -> параметры события).
- [postprocess](../numass-processing/src/postprocess.rs) - (оцпиональное) преобразование типа events -> events. На этом этапе производится обработка событий (например, фильтрация по виртуальному мертвому времени, объединение близких событий).

## Отладка
Обработка данных в программе реализована в 2-х вариациях:
- отладочный режим - детальная обработка небольшого количества кадров с детальной информацией (включая графическую)
- batch режим - обработка большого количества данных без графики.

Требование к отладке: **в batch-режиме выполняется ровно тот же код, что и при
визуальном тестировании**, чтобы не «наиграть» ошибок в отдельной batch-ветке.
Разница — только отключение отрисовки, а не замена алгоритма.

Реализована через опциональную фичу `egui` и проброс аргумента `#[cfg(feature = "egui")] ui: &mut Option<&mut PlotUi>,` во все функции обработки. Получается 3 режима:
| Режим | Условие | Назначение | Отрисовка |
| --- | --- | --- | --- |
| Медленный | `egui` + `ui = Some(..)` | одиночный кадр (filtered-viewer) | есть |
| Быстрый | `egui` + `ui = None` | пакетная обработка, но в рамках вьювера | нет |
| Самый быстрый | без фичи `egui` | неграфическая обработка ([numass-analysis](../numass-analysis)) | не компилируется |

## Обработка ошибок

В модуле намеренно используется `panic!` на любой ошибке вместо её обработки:
либо выполняется ровно то, что задумано, либо программа крашится, а не молча
выдаёт некорректный результат. Это упрощает поиск расхождений ценой отсутствия
восстановления после ошибки.

## Интерфейс
Для конфиграции обработки используется трейт
```rust
pub trait UserInput {
    // draw input form and read changes from it
    fn input(&self, ui: &mut egui::Ui, ctx: &egui::Context) -> Self;
}
```.
Каждый конфигурируемый элемент должен реализовывать этот трейт. На вход идут текущие значения, на выход — новые значения. Реализация трейта должна отрисовывать egui виджет элемента и считывать из него новые значения.

## Связность стадий

Стадии связаны через два разных значения и представление «события + метаданные точки»:

- `PreprocessParams` — упорядоченный список шагов waveform → waveform (`Fir`,
  `Baseline`, `Invert`). Preprocess материализует кадры в `f32` и проводит каждый
  шаг один раз. `Baseline::Point` читает уже записанный буфер и фильтр заново не
  гоняет. Сырые `i16` остаются borrow-ом protobuf.
- `StaticPointParams` — метаданные точки (`hv`, времена, `frame_len`, `bad_blocks`).
  Считается из метаданных и точки, без алгоритма и без базовой линии.
- Process читает стандартизованный кадр (`samples`, `delay`) и сырые коды там,
  где порог задан в кодах АЦП (reset, overflow). `emulate_fir` process не вызывает.
  Сдвиг времени берётся из `delay`, который записал шаг FIR.
- Postprocess использует из `StaticPointParams` только `bad_blocks` и `frame_len`.
  `cut_bad_blocks` применяется и когда `merge_close_events = false`.

`process` и `postprocess` друг о друге не знают. Process не выбирает цепочку
preprocess: связка по умолчанию — это `PreprocessParams::default` вместе с
`ProcessParams::default`. Именованные цепочки (`PreprocessParams::trapezoid`,
`::average`, `::trapezoid_fir`, `::empty`) остаются явным выбором вызывающего
и в тело алгоритма не зашиты.
